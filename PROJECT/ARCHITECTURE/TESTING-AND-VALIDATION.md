# APS 测试与验证规范

> 状态：当前施工规范  
> 分支：architecture-rebuild  
> 定位：建立可持续扩展的工程验证骨架，不把当前实现方式锁死。

## 一、核心原则

APS 采用**云端验证前置、真机验证后置**。

能在云端可靠证明的问题，不把真机作为主要测试场。APK 是工程验收产物，不是日常开发测试工具。

测试体系必须服务于长期演进：今天只有 GitHub 和本地文件，不代表以后只有这些能力。测试边界应围绕职责、接口和业务契约建立，而不是绑定某一个外部服务或当前 UI。

不因为建立测试体系而强行多模块化、不为了测试制造大量空壳层。只有当代码规模、构建速度、依赖边界或独立发布需求真正要求时，才升级为 Gradle 多模块。

## 二、整体流程

```
需求 / 问题
 ↓
业务链 / 验收条件
 ↓
模块职责与边界
 ↓
数据 / 状态 / 权限 / 接口约定
 ↓
最小施工
 ↓
代码级检查
 ↓
模块测试
 ↓
契约测试
 ↓
功能 / 业务链测试
 ↓
云端工程验证
 ↓
必要时生成 APK
 ↓
少量真机验收
 ↓
Verify / 收口
 ↓
PR / 合并
 ↓
main 正式构建
```

不是所有修改都必须经过全部层级。小范围纯文档或低风险修改可以缩短流程；改变核心业务链、状态、权限、外部能力边界时必须提高验证等级。

## 三、测试分层

### 1. 模块测试

验证一个职责明确的模块输入、状态和输出。

第一批优先：
- CommandParser
- PermissionPolicy
- ProjectTaskStateService
- ConstructionLockStore

这类测试应尽量不依赖真实网络、真实 GitHub 或 Android 页面。

### 2. 契约测试

验证模块之间的约定，而不是重复验证单个函数。

APS 当前重点契约：
- Task RUNNING → 才允许施工；
- 写入类执行 → 必须满足权限；
- Project 施工 → 必须持有对应 ConstructionLock；
- Commit → 必须满足 Project、Task、Member、GitHub 写入边界；
- Verify → 必须绑定实际 Commit / Run 证据。

契约测试是防止“改了一个模块，另一个模块悄悄失效”的主要闸门。

### 3. 功能 / 业务链测试

验证真实业务链是否可以组合工作：

```
Project
 → Address
 → Default Member
 → Conversation
 → Permission
 → Task
 → Execution
 → ConstructionLock
 → Commit
 → GitHub
 → Actions
 → Verify
```

业务链测试不要求每次都访问真实外部服务。外部能力应允许使用测试实现，以验证 APS 自己的业务编排是否正确。

### 4. 真机验收

只保留云端无法可靠证明的内容：
- 安装、启动；
- 页面布局、点击、滚动；
- 键盘和输入区；
- Android 生命周期；
- 系统权限弹窗；
- 实际设备上的网络行为；
- 真实 API 环境；
- 真实 GitHub 环境；
- 最终用户体验。

## 四、测试替身与外部能力

外部能力必须尽量通过清晰边界接入，使测试可以替换实现。

目标结构：

```
APS 业务逻辑
    ↓
能力接口 / 清晰边界
   ↙ ↘
真实实现   测试实现
```

适用对象包括：
- GitHub；
- API；
- 本地文件系统；
- 持久化；
- Actions / Verify 数据源。

测试实现可以返回固定、可预测的结果，用于验证业务逻辑；真实实现只在集成验证和必要的真机验收中使用。

不得为了测试把生产代码做成测试专用分支，也不得让测试实现改变产品语义。

## 五、Gradle 多模块边界

当前 APS 保持单 `app` 模块。

只有出现以下情况之一，才评估拆分 Gradle Module：
- 模块职责已经稳定且依赖方向明确；
- 构建时间明显受影响；
- 某部分需要独立复用；
- 某部分需要独立测试 / 发布；
- 依赖隔离能够明显降低修改风险。

在此之前，优先通过包、类、接口、Store、Service、Module 边界实现可测试性。

## 六、CI 演进

CI 不一次性做成复杂流水线，而是逐步增加闸门：

```
阶段一：代码检查 + 核心自动化测试
阶段二：模块 + 契约测试
阶段三：业务链测试 + 工程构建
阶段四：main 正式构建 + Release
```

测试越接近业务和外部环境，执行成本越高，越不应该成为每次最小修改的第一道闸门。

## 七、证据规则

自动化测试至少记录：
- 测试类型；
- 对应 Commit；
- 测试结果；
- 失败测试名称及原因。

Actions 验证至少记录：
- Workflow 类型；
- Run 编号；
- Run ID；
- Commit；
- Job；
- Artifact；
- 最终结果。

真机验收至少记录：
- APK 对应 Commit / Run；
- APK / 构建信息；
- 实际操作；
- 实际结果；
- 未通过项目。

没有证据，不标记“已验证”。

## 八、失败处理

普通实现缺陷：

```
失败
 ↓
定位
 ↓
最小修复
 ↓
对应测试回归
 ↓
继续业务链验证
```

出现以下情况时进入**重写候选**：
- 一个模块同时承担多个独立职责；
- 修复一个问题持续破坏多个无关能力；
- 测试无法隔离且必须依赖大量真实环境；
- 新增功能只能继续堆兼容代码；
- 状态、权限或数据归属出现多个真相来源；
- 继续修补的成本明显高于重新建立清晰边界。

重写候选不是立即重写，而是暂停继续堆补丁，先判断边界和迁移成本。

## 九、与施工流程的关系

测试不是“全部代码写完之后统一测试”。

采用：

```
小模块
 ↓
模块验证
 ↓
收口
 ↓
下一模块
 ↓
契约验证
 ↓
业务链验证
 ↓
整体工程验证
```

每经过一条真实业务链，都同时承担必要的审查、迁移和验证。

## 十、当前实施

当前阶段：

**主链收口 + 云端测试体系建设 + 验证。**

下一步先盘点并建立：
1. `src/test`；
2. `src/androidTest`；
3. Gradle 测试配置与依赖；
4. 核心模块测试；
5. 模块之间的契约测试；
6. Project 主链测试；
7. CI 测试闸门。

第一批测试不追求覆盖率数字，而追求把**Task、Permission、ConstructionLock、CommandParser**四个高价值边界真正变成可重复验证的工程事实。
