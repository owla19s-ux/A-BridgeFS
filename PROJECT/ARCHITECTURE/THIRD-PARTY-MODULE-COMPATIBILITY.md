# 第三方开源模块接入与兼容规范

状态：架构设计基线，待实现与验证

## 1. 目标

APS 应优先复用成熟的开源模块，而不是重复实现已有能力。接入新模块时，尽量只增加依赖和适配器，不要求修改 APS 核心业务模型。

本规范定义模块接入边界、兼容性评估、权限和验证要求。它不代表相关能力已经实现；实现状态必须由源码、测试和实际工作流确认。

## 2. 基本原则

1. **核心稳定，边缘适配**：APS 内部使用稳定的 Connection / Connector / Resource 契约；外部库通过适配器接入。
2. **按能力接入，不按仓库接入**：评估并引入所需的库或子模块，不默认复制整个仓库。
3. **显式依赖**：模块版本、来源、许可证和依赖关系必须可追溯。
4. **最小权限**：模块只获得当前任务所需的文件、网络、GitHub 或设备能力。
5. **可独立验证和替换**：模块故障、升级或移除，不应迫使无关业务模块重写。
6. **兼容性以证据为准**：README 声明不等于兼容；必须通过构建、契约测试和必要的集成测试。
7. **不提前拆分工程**：当前继续保持单 app 模块；只有复用、依赖隔离、构建耗时或团队协作等真实需求证明有收益时，再评估 Gradle 多模块化。

## 3. 接入类型与策略

| 类型 | 示例 | 默认接入策略 |
| --- | --- | --- |
| AI 服务 / 模型 API | OpenAI 兼容 API、厂商 API | 实现或扩展 AI Connector；配置模型、认证、流式能力、超时和错误映射 |
| 远程服务 API | REST / GraphQL 服务 | 使用独立 API / Service Connector；不要把业务服务逻辑塞进 UI |
| Kotlin / Java 库 | 文件解析、差异比较、代码分析 | 先评估许可证、Android API、传递依赖与维护状态，再通过小型适配器调用 |
| GitHub API / 工程工具 | 仓库读取、差异分析、工作流查询 | 复用合适的库或现有 GitHub API 层；权限与写入策略仍由 APS 控制 |
| Android UI / 功能模块 | 独立 Activity、组件或 SDK | 检查 Manifest、生命周期、主题、导航、资源命名和依赖冲突后再集成 |
| 独立服务 / 命令行程序 | Python、Node.js、原生 CLI | 默认不视为可直接嵌入 Android；评估远程服务、独立进程或替代实现，不能假定运行环境存在 |
| APS 内部模块 | Store、Dispatcher、Connector | 遵守模块职责与契约；不得绕过统一权限和持久化边界直接操作其他模块状态 |

## 4. Connector 最小契约

每个可被 APS 调用的能力适配器，应明确以下内容；具体接口按能力类型确定，不要求所有 Connector 强行实现相同的业务方法。

- **身份**：稳定的 Connection ID、类型和显示名称；不得用显示名称作为唯一身份。
- **能力声明**：支持哪些操作、输入格式、输出格式和可选能力。
- **执行语义**：同步 / 挂起、流式输出、取消支持、超时行为。
- **失败语义**：认证失败、权限不足、网络错误、限流、无效输入、部分成功和可重试错误的区分。
- **权限声明**：读取、修改、执行、网络访问等能力分别授权；默认拒绝未授权的写操作。
- **资源定位**：Address 用于定位，Resource 表示实际内容；不得把仓库地址、文件路径或显示名称混为同一概念。
- **可观测性**：返回可检查的结果和错误；日志不得记录 API Key、访问令牌或其他凭证。
- **版本兼容**：外部库版本和适配器版本可追溯；接口变更需更新契约测试。

AI Connector 当前已有 send、sendStreaming、cancelCurrentRequest 的基础契约。其他 Connector 不应为了形式一致而虚构无意义的操作；应定义公共生命周期 / 能力描述，并保留各自的类型安全接口。

## 5. 兼容性检查清单

每次引入或升级第三方模块，至少检查：

- [ ] 来源仓库、固定版本或 commit、维护状态可追溯；
- [ ] 许可证允许 APS 预期的使用、分发和修改方式；
- [ ] 支持当前 Kotlin / Java、Gradle、Android Gradle Plugin 和最低 Android API；
- [ ] 传递依赖没有不可解决的版本冲突、重复类或体积风险；
- [ ] 不要求缺失的系统能力、后台执行权限或不适用的运行时；
- [ ] 网络、文件、凭证和 GitHub 写入行为已检查；
- [ ] 异常、超时、取消、重试和资源释放行为可控；
- [ ] 通过构建与单元测试；跨边界能力通过契约测试；
- [ ] 关键路径通过集成测试；失败时可禁用或回退；
- [ ] 文档记录引入理由、已知限制和移除方式。

对不适合 Android 的项目，应明确标记为“不能直接嵌入”，而不是通过强行移植制造高维护成本。

## 6. 权限与安全边界

1. 第三方模块不得自行决定 APS 的用户授权状态。
2. 文件读取与写入、GitHub 读取与修改、工作流触发、外部 API 调用应分别受对应 Connection / Connector 的策略约束。
3. 凭证由专门的安全存储管理；不传入 UI 文本、不写入普通日志、不纳入错误信息。
4. 外部数据按不可信输入处理；路径、URL、仓库和分支参数须验证。
5. 对不可逆或影响远程状态的操作，必须有明确授权、结果确认和可追溯证据。
6. 第三方库不能通过直接调用底层客户端绕开 APS 的权限门禁；适配器应集中执行策略。

## 7. 测试分层

- **单元测试**：验证适配器输入输出映射、错误映射、权限门禁和参数校验。
- **契约测试**：验证实现符合 APS 对外约定；替换实现后可复用同一组契约测试。
- **集成测试**：验证真实 Android / 网络 / GitHub / 本地文件边界；可使用受控测试替身，涉及真实服务的测试应单独标记。
- **回归验证**：新模块不能破坏现有 AI、GitHub、Local、Context 和 Conversation 主链。
- **发布门禁**：必须运行相关测试；不能只凭编译成功或模块自述判断兼容。

## 8. 分阶段实施

### 阶段 A：建立清单与契约（当前优先）

- 盘点 AI、GitHub、Local 当前接口和已验证能力。
- 为每条能力标记：已实现、已测试、集成验证通过、缺失、阻塞。
- 确定公共错误、权限、能力声明与版本策略的最小范围。
- 暂不引入大型插件运行时，也不为了抽象而创建空泛接口。

### 阶段 B：选取一个真实开源模块试接入

- 从用户发现的模块中选一个价值明确、许可证清晰、Android 兼容性可确认的项目。
- 先做依赖和风险评估，再实现薄适配器。
- 验证可接入、可测试、可替换；记录接入成本和对核心代码的影响。

### 阶段 C：按真实需求扩展

- 当多个模块确实需要动态发现、启停或独立版本管理时，再设计插件清单与生命周期。
- 当依赖隔离、复用或构建时间出现明确收益时，再评估 Gradle 多模块。
- 未经独立威胁评估，不执行任意第三方代码动态加载。

## 9. 当前已知缺口

根据当前正式架构与状态文档，以下不能被视为已完成：

- Local Connector 的通用能力和边界仍需继续收口；
- GitHub 的部分施工接口仍带有旧本地文件语义；
- AI Connector 的基础接口已存在，但不同服务的能力差异、错误语义和安全地址校验仍需逐项验证；
- 尚无证据证明任意第三方模块都可直接接入 APS；
- 本规范本身是设计文件，不代表上述缺口已被代码修复。

## 10. 完成标准

只有同时满足以下条件，才能把某个第三方模块标记为“已接入”：

1. 接入类型、版本、来源与许可证已记录；
2. 有明确的 APS 适配边界；
3. 权限和安全检查通过；
4. 对应单元 / 契约测试通过；
5. 必要的集成测试与目标工作流通过；
6. 失败路径、限制和移除方式有记录。

模块是否接入成功，以代码和实际验证证据为准，不以文档状态或 AI 声明代替。
