# UI

正式 UI 资料入口。

当前 APS 第一阶段正式 UI 为三页：

- **空间页**：以空间为总名称和主要人机工作面；
- **对话页**：独立 AI 对话能力；
- **设置页**：全局连接、权限与系统配置。

其中，**空间页**是 APS 面向用户的主要工作页面。

## 一、空间与上下文：正式定义

### 1. 空间

**空间（Space）是 APS UI 中固定的顶层概念。**

空间承担一组相关内容的**总名称和总容器边界**。

空间名称由用户自定义，例如：

- A-177
- APS
- 角色世界
- 图片工具

UI 中只使用“空间”，不使用“项目空间”“工作空间”等前缀或复合名称。

空间本身不限定用户里面具体放什么，也不要求空间内内容采用统一的业务名称。

### 2. 上下文

**上下文（Context）是“空间”在语义层和代码层对应的核心概念。**

固定关系：

```
用户 / UI
    ↓
空间（Space）
    ↓
上下文（Context）
    ↓
资源、任务、对话、状态、记录、AI 协作……
```

因此：

- UI 对用户称为 **空间**；
- 领域语义 / 数据模型使用 **Context**；
- 一个空间对应一个 Context；
- 空间的自定义名称是 Context 的显示名称；
- Context 不直接等同于某一个 GitHub 仓库、本地目录或其他资源；
- Context 可以关联多个资源；
- Context 是 APS 组织连续工作状态的边界。

**Context 是内部语义，不要求在普通 UI 中直接显示“上下文”一词。**

### 3. 空间不是资源

空间与资源严格区分：

```
空间：A-177
│
├── 资源
│   ├── GitHub 仓库
│   ├── 本地目录
│   └── 其他资源
│
├── 任务
├── 对话
├── AI
├── 状态
└── 验证 / 工作记录
```

例如：

```
空间：A-177

资源：
- GitHub：owla19s-ux/A-177
- 本地：/Documents/A-177
```

GitHub 和本地都是空间关联的资源，不是空间本身。

因此原先的“Project Address”概念在 UI 语义上调整为：

> **空间中的资源 / 地址**

一个空间可以添加多个资源，也可以同时存在 GitHub、本地以及未来其他类型资源。

## 二、三页总览

```
APS
├─ 空间页
│  └─ Space / Context 的主要人机工作面
├─ 对话页
│  └─ 独立 AI 对话 / 查询 / 测试
└─ 设置页
   └─ 全局资源与系统设置
```

## 三、空间页

### 定位

**空间页 = 当前空间（Context）的主要人机工作面。**

它不是完整 Agent Runtime，也不是复杂的 Agent Engine。

空间页主要展示和操作：

- 空间名称；
- 空间关联的资源；
- 当前任务；
- AI / 协作；
- 空间内主要对话；
- 状态；
- 验证 / 工作记录。

### 空间名称

空间名称由用户自由定义。

```
空间

A-177
APS
角色世界
图片工具
```

名称只用于标识这个空间，不规定空间的实际内容类型。

### 空间资源

空间可以添加多个资源。

```
空间：A-177

资源
├── GitHub
│   └── owla19s-ux/A-177
├── 本地
│   └── /Documents/A-177
└── 其他
```

资源通过对应 Connector 访问：

```
Local → Local Connector → Android 本地资源
GitHub → GitHub Connector → GitHub API → Repository
```

空间不默认复制或同步这些资源。

### 空间配置

空间配置通过独立入口展开 / 收起，不与主要工作内容混成一个长面板。

配置内容可以包括：

- 空间名称；
- 资源；
- AI 配置；
- 权限；
- 其他空间级设置。

### 空间内对话

空间主要对话是空间工作面的组成部分。

任务与对话保持不同职责：

- **任务**：需要处理的工作事项；
- **对话**：人与 AI 或 AI 之间的交流及工作记录。

### AI / 协作

空间提供 AI 协作入口。

当前 UI 不固定 Decision AI、Worker AI、AI A、AI B 等角色分类。

AI 的具体分工由实际任务和调度结果决定。

### 状态 / 验证

空间页面可以展示当前工作状态和验证结果。

AI 的口头结果不能直接作为事实状态；需要结合实际结果、验证或其他证据形成工作记录。

### ↑ / ↓

底部 ↑ / ↓ 只控制屏幕显示空间：

- 不自动改变任务状态；
- 不改变对话状态；
- 不改变空间业务状态。

---

## 四、对话页

**定位：直接使用 API 进行普通 AI 对话、查询和测试。**

可以：

- 选择 / 切换 API Profile；
- 与单个 AI 对话；
- 在授权范围内读取当前空间可访问的资源。

对话页不自动获得空间施工权限，也不自动启动多 AI 协作。

---

## 五、设置页

**定位：全局资源与系统设置。**

主要包括：

- API Profiles；
- GitHub；
- 系统级权限；
- 其他全局配置。

模块自己的权限继续由模块管理；空间级访问范围由空间 / Context 管理。

---

## 六、页面边界

```
                    APS
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        空间页      对话页      设置页
          │          │           │
      空间工作      AI 对话      全局资源
          │          │           │
    资源/任务/状态  API/查询      连接/权限
          │
       AI 协作
```

三页不得重新互相吞并职责。

---

## 七、已废弃的 UI 模型

以下模型不再作为 APS 当前 UI 的正式概念：

- Project 作为顶层 UI 概念；
- Project Address 作为空间唯一地址；
- 一个 Project 对应一个主要资源地址；
- Decision AI 固定分类；
- Worker AI 固定分类；
- 固定 AI A / AI B；
- 工作区作为独立一级业务页面；
- 通过 AI 角色直接定义决策 / 施工职责；
- 复杂 Project Dashboard。

其中：

> **“项目”可以继续作为用户自定义的空间名称，但不再是 APS 的固定 UI 概念。**

---

## 八、UI 与语义层的固定映射

```
UI：空间
   │
   │ 一对一
   ↓
语义 / 数据：Context
   │
   ├── Resources
   ├── Tasks
   ├── Conversations
   ├── AI / Collaboration
   ├── State
   └── Receipts / Verification
```

后续架构、数据模型和代码设计必须以这一映射为前提。

**本文件负责锁定 UI 层的“空间 / Context”关系；在此关系确定后，再继续调整架构和产品规格文档。**
