# UI

正式 UI 资料入口。

当前 APS 第一阶段正式 UI 为三页：

- **空间页**：进入和管理空间连接，并展示其中的 Context；
- **对话页**：独立 AI 对话能力；
- **设置页**：全局连接、权限与系统配置。

其中，**空间页**是 APS 面向用户的主要人机工作页面。

## 一、空间、连接、调度与 Context：正式定义

### 1. 空间

**空间（Space）是 APS 中的一种连接，不是普通的 UI 文件夹、项目目录或个人资料区。**

空间代表一个可以被 APS 连接、进入、组织和使用的环境。它可以来自手机本地、PC、其他设备、云端、NAS 或未来由插件提供的其他空间。

空间也可以具有不同的可见性或访问方式，例如个人/不公开、公开以及未来其他共享方式。这些是空间属性，不改变空间作为一种连接的定义。

### 2. 连接

**连接（Connection）是 APS 的核心基础概念之一。**

连接不限于 API，可以包括：

- 空间；
- AI；
- GitHub；
- 本地资源；
- 设备；
- 文件；
- API / 服务；
- 插件；
- 其他未来能力。

因此：**空间是连接的一种，AI 也是连接的一种。**

连接不规定 APS 的具体业务用途。

### 3. 调度

**调度（Dispatcher）是 APS 的另一项核心基础能力。**

调度负责根据当前状态和任务需要组织、选择和调用连接。

```text
Context
   ↓
调度
   ├── AI 连接
   ├── GitHub 连接
   ├── 本地连接
   └── 其他连接
```

APS 不要求 Context 固定绑定某一个 AI。AI 是连接，不是 Context 的固定组成部分。

### 4. Context

**Context 是 APS 的内部语义 / 数据概念，不是用户必须看到的 UI 名称。**

Context 表示空间中一个具体的、可独立承载状态和内容的上下文。

例如：

```text
项目空间：APS 开发
├── APS（Context）
├── A-177（Context）
└── 其他项目（Context）
```

这里“APS”“A-177”等都是用户自定义的显示名称；Context 是代码和数据模型使用的统一语义。UI 不要求用户使用“Context / 上下文”这个词。

Context 不限定必须是项目，也可以是游戏灵感、角色资料、旅行计划等其他用户定义的内容。

**Context 的具体显示名称完全由用户自定义。**

## 二、空间内部组织

空间本身是连接；空间内部可以按照用户需要进行组织。

例如：

```text
空间
│
├── 项目空间：APS 开发
│    ├── APS（Context）
│    ├── A-177（Context）
│    └── 其他项目（Context）
│
├── 作品空间：我的作品
│    ├── 作品A（Context）
│    └── 作品B（Context）
│
└── 个人沉淀空间：我的资料
     ├── 技术研究（Context）
     └── 灵感记录（Context）
```

“项目空间”“作品空间”“个人沉淀空间”是空间内部的组织方式 / 分组概念，不是 APS 顶层固定业务类型；名称和具体组织方式可以由用户决定。

## 三、Context 的内容边界

Context 是具体内容的承载边界，可以包含：

- 资源；
- 连接；
- 任务；
- 对话；
- 状态；
- 工作记录；
- 验证；
- 调度所需状态。

例如：

```text
APS（Context）
│
├── 资源
├── 连接
├── 任务
├── 对话
├── 状态
├── 工作记录
└── 验证
```

注意：**AI 不属于 Context 的固定模块。** 正确关系是 Context → 调度 → AI 连接 / GitHub 连接 / 本地连接 / 其他连接。

一个 Context 可以使用一个、多个或不同类型的连接，也可以没有 AI 连接。

## 四、资源与地址

空间或 Context 可以关联多个资源，例如：

```text
APS（Context）
资源：
- GitHub：owla19s-ux/APS
- 本地：/Documents/APS
- 其他资源
```

资源通过对应 Connector 访问。APS 不默认复制或同步这些资源。

原先的 Project Address 概念调整为：**资源 / 地址是连接所指向的内容，不是空间本身。**

## 五、三页总览

```text
APS
├─ 空间页
│  └─ 空间连接 / Context 的主要人机工作面
├─ 对话页
│  └─ 独立 AI 对话 / 查询 / 测试
└─ 设置页
   └─ 全局连接与系统设置
```

## 六、空间页

**空间页 = 用户进入、选择和管理空间连接，并进入具体 Context 的主要人机工作面。**

主要展示和操作：空间、空间内部组织、Context、Context 资源、任务、对话、状态、工作记录、验证、连接和调度相关状态。

空间名称、组织名称、Context 显示名称均由用户定义。

空间页可以展示和管理当前可用连接，例如 AI、GitHub、本地、设备、插件及其他服务。调度状态和结果也可以在此展示。

APS 不固定 Decision AI、Worker AI、AI A / AI B 或永久主 AI。具体由调度和连接状态决定。

AI 的口头结果不能直接作为事实状态，需要结合实际结果、验证或其他证据形成工作记录。

## 七、对话页

**定位：直接使用 AI 连接进行普通 AI 对话、查询和测试。**

可以选择 / 切换 AI 连接，与单个 AI 对话，并在授权范围内读取当前 Context 可访问的资源。

对话页不自动获得 Context 的全部操作权限，也不自动启动多连接调度。

## 八、设置页

**定位：全局连接与系统设置。**

主要包括 AI / API 连接、GitHub 连接、其他全局连接、系统级权限和其他全局配置。

## 九、页面边界

```text
                    APS
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        空间页      对话页      设置页
          │          │           │
       空间连接      AI连接      全局连接
          │
       Context
          │
    连接 + 调度 + 内容
```

UI 页面只是 APS 的人机表现层，不重新定义 APS 的核心语义。

## 十、已废弃的 UI 模型

以下模型不再作为 APS 当前 UI 的正式概念：

- Project 作为 APS 顶层 UI 概念；
- Project Address 作为空间唯一地址；
- 一个 Project 对应一个主要资源地址；
- 空间 = 一个 Context；
- Context = 空间名称；
- AI 作为 Context 的固定组成部分；
- Decision AI / Worker AI / AI A / AI B 等固定角色分类；
- 工作区作为独立一级业务页面；
- 通过 AI 角色直接定义决策 / 施工职责；
- 复杂 Project Dashboard。

“项目”可以是用户自定义的 Context 名称，也可以用于描述一种组织方式，但不是 APS 的固定顶层 UI 概念。

## 十一、UI 与语义层的固定映射

```text
UI：空间
   │
   │ 作为一种连接
   ↓
空间连接
   │
   ├── 用户自定义组织
   │
   └── Context
        │
        ├── Resources
        ├── Tasks
        ├── Conversations
        ├── Connections
        ├── State
        ├── Records
        └── Verification
```

同时：

```text
APS
├── 连接
│    ├── 空间连接
│    ├── AI 连接
│    ├── GitHub 连接
│    ├── 本地连接
│    └── 其他连接
│
└── 调度
```

**本文件负责锁定 UI 层关于“空间、连接、调度、Context”的基本关系。** 后续架构、数据模型和代码设计必须以此为前提，但不得把 Context 直接暴露为用户必须理解的产品名称。

## 十二、空间页：分组管理与项目 / Context 列表补充定义

本节是在保留前述 UI 定义的基础上，对**空间页实际页面结构**进行补充。原有定义暂不删除或覆盖。

### 1. 分组管理

空间页在原有项目 / Context 列表**上方增加分组管理区域**。

分组管理的交互逻辑参考常见的对话分组管理方式：

```text
空间页
├── 分组管理
│   ├── 全部
│   ├── 用户自定义分组
│   ├── 用户自定义分组
│   └── ...
│
└── 项目 / Context 列表
```

分组用于帮助用户组织空间中的多个项目 / Context。

分组不是 APS 固定的业务类型。用户可以：

- 新建分组；
- 修改分组名称；
- 删除分组；
- 将项目 / Context 放入或移动到分组；
- 在分组之间切换；
- 查看全部项目 / Context。

例如：

```text
空间
│
├── 全部
│
├── 开发
│   ├── APS
│   ├── A-177
│   └── 图片工具
│
├── 作品
│   ├── 角色世界
│   └── 作品B
│
└── 其他
    └── ...
```

“开发”“作品”“其他”等均为用户自定义分组名称。

**分组只负责组织和筛选，不改变项目 / Context 本身的语义。**

### 2. 项目 / Context 列表保持原有直接入口

增加分组管理后，原有的项目 / Context 列表不拆成额外页面。

用户在当前分组下直接看到项目 / Context。

例如：

```text
分组：开发

APS
A-177
图片工具
```

点击具体项目 / Context 后，**仍然进入原有的具体内容 / 工作页面**。

因此页面关系为：

```text
空间页
   │
   ├── 上方：分组管理
   │
   └── 下方：项目 / Context 列表
                 │
                 └── 点击
                      ↓
                 具体内容页面
```

这里不新增“Context 管理页”，也不把 Context 强制作为用户可见的术语。

### 3. 项目 / Context 名称

项目 / Context 的显示名称由用户自定义。

例如：

- APS；
- A-177；
- 角色世界；
- 图片工具；
- 游戏灵感；
- 旅行计划。

“项目”只是当前常见的一种内容形式，不代表 Context 必须是软件项目。

### 4. 项目 / Context 地址

当前项目 / Context 的地址类型暂定为三类：

1. **本地**
2. **云端**
3. **其它**

第一阶段实际实现：

- **本地**
- **云端**

**其它**作为预留类型，当前不施工具体实现。

地址类型用于表示该项目 / Context 主要关联的地址来源。

例如：

```text
开发

APS          本地
A-177        云端
图片工具      本地
```

地址不是项目 / Context 的名称，也不是空间本身。

后续“其它”可以扩展为其他地址或连接来源，不改变当前 UI 的基本结构。

### 5. 当前空间页结构

现阶段空间页的结构可以暂定为：

```text
┌─────────────────────────────┐
│ 空间名称                    │
├─────────────────────────────┤
│ 分组：全部 / 用户自定义分组 │
├─────────────────────────────┤
│ 项目 / Context 列表         │
│                             │
│ APS                 本地    │
│ A-177               云端    │
│ 图片工具             本地    │
│                             │
└─────────────────────────────┘
```

该结构只确定**信息层级和交互关系**，暂不锁定具体视觉样式。

### 6. 当前阶段边界

本次补充只确定：

- 空间页增加分组管理；
- 分组位于项目 / Context 列表上方；
- 分组参考对话分组的管理方式；
- 原有项目 / Context 仍直接显示并可点击进入；
- Context 名称由用户自定义；
- 地址类型暂定本地 / 云端 / 其它；
- 第一阶段只施工本地与云端；
- 不新增独立 Context 管理页；
- 不删除前文已有 UI 定义。

后续再单独确定**点击项目 / Context 后的具体页面设计**。

## 十三、空间页 UI 细化与歧义收敛

本节用于在不删除前述历史定义的前提下，进一步锁定当前 UI 的实际结构。
当早期章节的描述较宽泛时，以本节对**当前第一阶段 UI 行为**的细化为准。

### 1. 空间页的定位

空间页表示**当前选中的一个空间**，不是“空间列表页 → 分组页 → Context 页”的多级浏览结构。

因此用户进入空间页后，应直接看到：

~~~text
当前空间
↓
分组管理
↓
Context 列表
~~~

多个空间的切换、增加或连接，可以通过空间页顶部的空间入口完成，但不再额外增加一层独立的“空间浏览首页”。

### 2. 空间页顶部

空间页顶部负责表达当前处于哪个空间，并提供与空间本身有关的基础操作。

信息关系固定为：

~~~text
┌─────────────────────────────┐
│ 当前空间名称        切换 / 管理 │
├─────────────────────────────┤
│ 分组                         │
│ 全部  开发  作品  其他 ...  │
├─────────────────────────────┤
│ Context 列表                 │
└─────────────────────────────┘
~~~

这里的“切换 / 管理”属于空间连接本身的操作，不改变下面 Context 列表的层级。

### 3. 分组不是下一层空间

“项目空间”“作品空间”“个人沉淀空间”等名称，只能作为用户自定义的**分组名称或组织名称**存在。

它们不表示：

~~~text
空间
└── 项目空间
    └── Context
~~~

这种固定的二级空间结构。

当前 UI 只使用：

~~~text
空间
├── 分组
│   ├── 分组A
│   ├── 分组B
│   └── ...
└── Context
    ├── Context A
    ├── Context B
    └── ...
~~~

这样可以避免把“空间”和“分组”混成两个不同层级的容器概念。

### 4. 分组的实际作用

分组只承担**组织、筛选和快速定位**作用，不创建新的内容承载边界。

第一阶段采用以下行为：

- `全部` 是系统固定的聚合视图；
- 用户可以创建、重命名、删除分组；
- 一个 Context 在同一时间归属于一个用户分组，也可以暂不归组；
- `全部` 显示当前空间中的所有 Context；
- 删除分组不会删除其中的 Context；
- 删除 Context 才会影响 Context 本身。

因此：

~~~text
全部
├── APS
├── A-177
├── 图片工具
└── ...

开发
├── APS
└── A-177

作品
└── 图片工具
~~~

其中“全部”不是实际存储分组，而是聚合显示。

### 5. Context 列表的最低信息层级

列表不承担 Context 的完整内容展示，只提供进入具体内容页面所需的信息。

第一阶段至少显示：

~~~text
Context 显示名称    地址类型
APS                 本地
A-177               云端
图片工具             本地
~~~

其中：

- **显示名称**：完全由用户定义；
- **地址类型**：本地 / 云端 / 其它；
- **实际地址**：不在列表中展开为长路径或完整地址，应在进入具体内容页面后查看和管理；
- **其它**：作为保留类型显示/识别，但第一阶段不实现其具体连接方式。

这样可以避免列表被文件路径、仓库地址等技术信息占满。

### 6. Context 与资源地址

Context 是内容承载边界；地址是 Context 所关联资源的来源信息。

两者关系为：

~~~text
Context
   │
   └── 地址类型
        ├── 本地
        ├── 云端
        └── 其它（预留）
~~~

但 Context 内部仍可以关联多个具体资源，例如：

~~~text
APS
├── 本地资源
│   └── /Documents/APS
├── 云端资源
│   └── GitHub / 其他云端服务
└── 其他资源
~~~

因此：

**“地址类型”用于 UI 中快速识别来源，“具体地址 / 资源”属于 Context 内部的详细内容。**

### 7. GitHub 不等于云端

第一阶段的“云端”必须保持为通用概念。

例如 GitHub 可以作为一种云端资源，但 UI 和数据定义不应写成：

~~~text
云端 = GitHub
~~~

正确关系是：

~~~text
地址类型：云端
        │
        ├── GitHub
        ├── 其他云端服务
        └── 未来其他云端连接
~~~

这样可以避免第一阶段就把 APS 的云端能力锁死在 GitHub。

### 8. 连接在空间页中的表现

连接是 APS 的基础能力，因此空间页需要能够使用空间连接及其相关连接，但**不再把各种连接全部做成 Context 列表中的固定子页面**。

第一阶段采用：

~~~text
空间页
├── 当前空间连接
├── 分组
└── Context 列表
       │
       └── 进入具体 Context
             ├── 内容
             ├── 资源
             ├── 任务
             ├── 对话
             ├── 连接
             ├── 状态
             ├── 工作记录
             └── 验证
~~~

AI、GitHub、本地等均通过“连接”参与，而不是作为每个 Context 都必须存在的固定入口。

### 9. AI 与对话页的关系

独立对话页用于直接使用 AI 连接。

Context 内的对话属于该 Context 的工作内容，可以使用 Context 当前可用的 AI 连接。

因此：

~~~text
对话页
└── 独立 AI 对话

Context
└── 对话
    └── 使用 AI 连接完成当前 Context 的工作
~~~

两者都可以调用 AI，但语义不同：

- 对话页：以 AI 对话本身为主；
- Context 对话：以 Context 的内容和状态为主。

不应因为二者都使用 AI，就把独立对话自动变成某个 Context 的子项。

### 10. 空间页不承担“所有能力总览”

空间页是主要工作面，但不等于把 APS 所有能力全部堆在一页。

页面优先级应保持：

~~~text
第一优先级：当前空间
第二优先级：分组
第三优先级：Context 列表
第四优先级：进入 Context 后使用具体能力
~~~

连接管理、全局权限、全局设置等仍由设置页承担。

空间页只需要提供完成当前空间工作所必需的入口。

### 11. 当前 UI 的完整关系

当前第一阶段可以统一为：

~~~text
APS
│
├── 连接
│   ├── 空间
│   ├── AI
│   ├── GitHub
│   ├── 本地
│   ├── 文件 / 设备 / API / 插件
│   └── 其他未来连接
│
└── 调度
    │
    └── 根据 Context 与任务需要组织连接
~~~

用户界面：

~~~text
APS
├── 空间页
│   │
│   ├── 当前空间
│   │
│   ├── 分组管理
│   │   ├── 全部
│   │   └── 用户自定义分组
│   │
│   └── Context 列表
│       ├── 用户自定义名称
│       ├── 地址类型
│       └── 点击进入具体内容页面
│
├── 对话页
│   └── 直接使用 AI 连接
│
└── 设置页
    └── 全局连接与系统配置
~~~

### 12. 第一阶段明确不做的事情

为避免 UI 在施工过程中再次膨胀，当前阶段明确不引入：

- 独立的 Context 管理页；
- 固定的“项目空间 / 作品空间 / 个人沉淀空间”三类页面；
- GitHub 专属的云端页面类型；
- AI 作为 Context 固定模块；
- Decision AI / Worker AI 等固定 AI 角色；
- 复杂 Dashboard；
- 在 Context 列表中直接展开全部资源、任务、对话和验证内容。

这些能力可以存在于后续具体页面或调度系统中，但不改变当前空间页的核心信息层级。

### 13. UI 锁定原则

后续 UI、数据模型和代码设计应遵守以下顺序：

~~~text
空间
  ↓
分组（组织 / 筛选）
  ↓
Context（实际内容承载）
  ↓
具体内容 / 工作页面
  ↓
连接 + 调度
~~~

其中：

- 空间是连接；
- 分组是组织方式；
- Context 是内部语义 / 数据对象；
- Context 显示名称由用户定义；
- 地址类型是 Context 的地址来源分类；
- AI 是连接；
- 调度负责组织连接；
- UI 不要求用户理解 Context 这一内部术语。

本节至此锁定**当前第一阶段空间页的信息层级与基本交互关系**。点击具体 Context 后的详细页面，另行设计。


## 十四、Context 详细页面 UI 设计

本节正式确定**点击空间页中的具体 Context 后进入的详细页面**。该页面是 Context 的实际内容 / 工作承载面，不再作为空间管理页的延伸，也不做成 APS 全能力 Dashboard。

### 1. 页面定位

Context 详细页面的唯一核心职责是：

> **让用户进入一个具体 Context，并在这个 Context 内查看内容、使用资源、发起任务、使用连接、查看状态和工作结果。**

页面关系固定为：

~~~text
空间页
  │
  └── 点击用户自定义的 Context 名称
          ↓
      Context 详细页面
          │
          ├── 内容
          ├── 任务
          ├── 对话
          ├── 资源
          ├── 连接
          └── 记录
~~~

这里的 Context 仍然只是内部语义。用户看到的是自己定义的名称，例如“APS”“角色世界”“旅行计划”等。

### 2. 页面整体骨架

第一阶段采用**顶部信息区 + Context 导航 + 主内容区**的结构：

~~~text
┌────────────────────────────────┐
│ ←  Context名称      地址类型  ⋯ │
│    本地 / 云端 / 其它          │
├────────────────────────────────┤
│ 内容  任务  对话  资源  连接  记录 │
├────────────────────────────────┤
│                                │
│          当前主内容区            │
│                                │
│   根据当前 Context 内容决定显示 │
│                                │
├────────────────────────────────┤
│ 当前状态 / 调度状态（按需显示） │
└────────────────────────────────┘
~~~

顶部和导航属于 Context 页固定结构；主内容区保持可扩展。

### 3. 顶部信息区

顶部固定提供：

- 返回空间页；
- Context 用户自定义名称；
- 当前地址类型；
- Context 基础操作菜单。

地址类型只表达来源分类：

~~~text
本地 / 云端 / 其它
~~~

第一阶段实际支持本地与云端；其它继续作为预留类型。

顶部不显示：

- 固定“项目”字样；
- 固定 GitHub 地址；
- AI 名称作为 Context 身份；
- 大量资源路径；
- 大量内部技术状态。

Context 的实际地址、资源列表和连接细节进入对应页面查看。

### 4. Context 内部导航

Context 页面固定提供一组**核心导航入口**：

~~~text
内容 | 任务 | 对话 | 资源 | 连接 | 记录
~~~

这些入口是“进入 Context 后的主要能力入口”，而不是要求每个 Context 都必须拥有大量固定数据。

各入口职责：

#### 内容

Context 的默认主页面。

内容区是整个 Context 最主要的工作区域，可以根据 Context 类型和已有资源显示不同内容。

例如：

- 软件项目可以显示代码相关内容；
- 作品可以显示素材和创作内容；
- 游戏创意可以显示设定资料；
- 个人沉淀可以显示笔记、资料或其他内容。

因此“内容”本身不能被写死成某一种编辑器。

#### 任务

查看和操作当前 Context 的任务。

主要显示：

~~~text
当前任务
待处理任务
已完成任务
失败 / 待验证任务
~~~

正在执行的任务可以显示简要调度状态。

任务页面不固定“主 AI / Worker AI”等角色；执行者由当前连接和调度状态决定。

#### 对话

只显示**属于当前 Context 的工作对话**。

对话可以调用当前 Context 可用的 AI 连接，但对话本身仍属于 Context 内容的一部分。

独立的普通 AI 对话仍由 APS 顶层“对话页”承担。

#### 资源

管理当前 Context 关联的具体资源和地址。

例如：

~~~text
资源
├── 本地资源
│   └── /Documents/APS
├── 云端资源
│   └── GitHub / 其他云端服务
└── 其他未来资源
~~~

一个 Context 可以关联多个资源，不限制为单一地址。

#### 连接

查看和管理当前 Context 可以使用的连接。

例如：

~~~text
连接
├── AI
├── GitHub
├── 本地
├── 设备
├── 文件
├── API / 服务
└── 其他连接
~~~

这里的连接类型可以持续扩展。

**AI、GitHub 等不是 Context 固定模块，而是连接列表中的具体连接。**

#### 记录

用于查看 Context 的工作过程和结果记录。

至少包括：

- 调度 / 执行记录；
- AI 或其他连接返回的结果摘要；
- 实际操作结果；
- 验证结果；
- 失败、重试和恢复记录。

记录的目标是让用户能回溯“做了什么、实际结果是什么、是否验证”。

### 5. 状态如何呈现

状态不单独占用一个固定一级页面。

Context 当前状态采用**紧凑状态区**表达：

~~~text
空闲
运行中
等待输入
等待连接
等待验证
已完成
失败
~~~

具体状态类型后续可以扩展。

当 Context 当前存在正在执行的任务时，在内容区或底部显示当前运行状态；没有运行任务时不强制显示大型状态面板。

这样可以避免 Context 页变成监控 Dashboard。

### 6. 调度如何呈现

调度是 APS 的核心能力，但**不作为 Context 页永久占据空间的独立 Dashboard**。

采用：

~~~text
用户操作
  ↓
任务
  ↓
调度
  ↓
选择 / 调用连接
  ↓
执行
  ↓
结果
  ↓
验证 / 记录
~~~

UI 上只需要提供清晰的“发起 / 执行 / 查看结果”入口。

当有任务运行时，Context 页面显示一个紧凑的当前调度状态：

~~~text
正在处理：任务名称
使用连接：若干连接
当前状态：运行中
[查看详情]
~~~

点击后进入任务 / 执行详情。

没有运行任务时，不显示永久性的调度控制面板。

### 7. 任务执行结果的展示原则

调度产生的结果必须区分：

~~~text
AI / 连接返回
       ↓
实际执行结果
       ↓
验证结果
~~~

用户在 Context 页面看到的完成状态，不应只依据 AI 的口头描述。

例如：

~~~text
任务：更新 APS UI 文档

执行结果：已提交修改
验证：通过
状态：已完成
~~~

或者：

~~~text
任务：更新 APS UI 文档

执行结果：已提交修改
验证：失败
状态：待处理
~~~

这样 Context 页可以成为真实工作结果的承载页面，而不是单纯的聊天记录页面。

### 8. 内容区的可扩展方式

Context 页真正需要长期保持开放的是**主内容区**。

固定的是页面骨架：

~~~text
顶部信息
  ↓
Context 导航
  ↓
主内容区
  ↓
状态 / 调度提示
~~~

可扩展的是：

~~~text
主内容区
├── 文本 / 文档
├── 文件 / 素材
├── 代码
├── 图片
├── 数据
├── 第三方服务内容
├── 插件提供的内容视图
└── 未来其他内容
~~~

这样 APS 不需要在第一阶段提前规定“Context 必须是项目页面、作品页面或笔记页面”。

### 9. 连接的使用方式

连接有两种层次：

**管理层：**

~~~text
Context → 连接
~~~

用户可以查看、添加、移除、授权当前 Context 可使用的连接。

**执行层：**

~~~text
任务 → 调度 → 连接
~~~

具体任务执行时，由调度根据任务和状态选择实际连接。

因此用户不需要手动把“AI / GitHub / 本地”等固定拼进页面流程；连接可以被不同任务按需调用。

### 10. Context 页中的操作优先级

页面操作优先级固定为：

~~~text
第一：查看 / 使用当前 Context 内容
第二：继续当前任务
第三：发起新任务
第四：查看资源、连接和工作记录
第五：管理 Context 本身
~~~

Context 管理本身放入顶部“⋯”菜单，例如：

- 重命名；
- 修改地址；
- 分组调整；
- 删除；
- 其他基础管理操作。

不在主内容区域放置大量管理按钮。

### 11. 手机上优先的交互方式

考虑 APS 的主要使用端为 Android 手机，Context 页优先采用：

- 顶部固定返回和名称；
- 横向可滚动的 Context 导航；
- 主内容区单列展示；
- 运行状态采用紧凑卡片或状态条；
- 长地址、日志、记录等进入独立详情页面；
- 不使用依赖大屏幕的复杂多栏布局作为第一阶段基础结构。

需要同时兼容平板或桌面时，再在同一信息层级上扩展为双栏 / 多栏布局，而不改变语义。

### 12. 固定内容与可扩展内容

**第一阶段固定：**

~~~text
Context
├── 顶部信息
├── 内容
├── 任务
├── 对话
├── 资源
├── 连接
└── 记录
~~~

**保持可扩展：**

~~~text
内容类型
连接类型
资源类型
任务类型
记录 / 验证类型
插件提供的内容视图
~~~

**不固定：**

- 某一种项目类型；
- 某一种编辑器；
- 某一种 AI；
- 某一种云端服务；
- 某一种执行角色；
- 某一种工作流。

### 13. Context 详细页面最终结构

当前第一阶段正式收敛为：

~~~text
空间页
  │
  └── Context
       │
       ├── 顶部
       │   ├── 返回
       │   ├── 用户自定义名称
       │   ├── 地址类型
       │   └── 基础管理
       │
       ├── Context 导航
       │   ├── 内容
       │   ├── 任务
       │   ├── 对话
       │   ├── 资源
       │   ├── 连接
       │   └── 记录
       │
       ├── 主内容区
       │   └── 可扩展
       │
       └── 按需状态 / 调度信息
~~~

这个结构将 Context 定位为 APS 的**具体内容与工作的实际承载面**，同时把连接和调度保持为可调用的基础能力，而不是固定业务页面。

### 14. 本阶段 UI 边界

本节锁定 Context 页的**结构和信息层级**，暂不锁定：

- 具体图标；
- 颜色；
- 字体；
- 卡片圆角；
- 动画；
- 精确按钮位置；
- 具体内容插件样式。

下一阶段应在此结构不变的前提下，继续细化：

> **“内容”默认首页到底显示什么，以及任务、连接、资源、记录四类页面的具体手机端布局。**
