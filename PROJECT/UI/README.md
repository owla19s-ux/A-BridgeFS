# UI

正式 UI 资料入口。

当前 APS 第一阶段正式 UI 为三页：

- **空间页**：进入和管理空间连接，并展示其中的 Context；
- **对话页**：独立 AI 对话能力；
- **设置页**：全局连接、权限与系统配置。

其中，**空间页**是 APS 面向用户的主要人机工作页面。

## 一、空间、连接、调度与 Context：正式定义

### 1. 空间

**空间（Space）是 APS 中的一种连接，不是普通的 UI 文件夹、项目目录或个人资料区。**

空间代表一个可以被 APS 连接、进入、组织和使用的环境。它可以来自手机本地、PC、其他设备、云端、NAS 或未来由插件提供的其他空间。

空间也可以具有不同的可见性或访问方式，例如个人/不公开、公开以及未来其他共享方式。这些是空间属性，不改变空间作为一种连接的定义。

### 2. 连接

**连接（Connection）是 APS 的核心基础概念之一。**

连接不限于 API，可以包括：

- 空间；
- AI；
- GitHub；
- 本地资源；
- 设备；
- 文件；
- API / 服务；
- 插件；
- 其他未来能力。

因此：**空间是连接的一种，AI 也是连接的一种。**

连接不规定 APS 的具体业务用途。

### 3. 调度

**调度（Dispatcher）是 APS 的另一项核心基础能力。**

调度负责根据当前状态和任务需要组织、选择和调用连接。

```
Context
   ↓
调度
   ├── AI 连接
   ├── GitHub 连接
   ├── 本地连接
   └── 其他连接
```

APS 不要求 Context 固定绑定某一个 AI。AI 是连接，不是 Context 的固定组成部分。

### 4. Context

**Context 是 APS 的内部语义 / 数据概念，不是用户必须看到的 UI 名称。**

Context 表示空间中一个具体的、可独立承载状态和内容的上下文。

例如：

```
项目空间：APS 开发
├── APS（Context）
├── A-177（Context）
└── 其他项目（Context）
```

这里“APS”“A-177”等都是用户自定义的显示名称；Context 是代码和数据模型使用的统一语义。UI 不要求用户使用“Context / 上下文”这个词。

Context 不限定必须是项目，也可以是游戏灵感、角色资料、旅行计划等其他用户定义的内容。

**Context 的具体显示名称完全由用户自定义。**

## 二、空间内部组织

空间本身是连接；空间内部可以按照用户需要进行组织。

例如：

```
空间
│
├── 项目空间：APS 开发
│    ├── APS（Context）
│    ├── A-177（Context）
│    └── 其他项目（Context）
│
├── 作品空间：我的作品
│    ├── 作品A（Context）
│    └── 作品B（Context）
│
└── 个人沉淀空间：我的资料
     ├── 技术研究（Context）
     └── 灵感记录（Context）
```

“项目空间”“作品空间”“个人沉淀空间”是空间内部的组织方式 / 分组概念，不是 APS 顶层固定业务类型；名称和具体组织方式可以由用户决定。

## 三、Context 的内容边界

Context 是具体内容的承载边界，可以包含：

- 资源；
- 连接；
- 任务；
- 对话；
- 状态；
- 工作记录；
- 验证；
- 调度所需状态。

例如：

```
APS（Context）
│
├── 资源
├── 连接
├── 任务
├── 对话
├── 状态
├── 工作记录
└── 验证
```

注意：**AI 不属于 Context 的固定模块。** 正确关系是 Context → 调度 → AI 连接 / GitHub 连接 / 本地连接 / 其他连接。

一个 Context 可以使用一个、多个或不同类型的连接，也可以没有 AI 连接。

## 四、资源与地址

空间或 Context 可以关联多个资源，例如：

```
APS（Context）
资源：
- GitHub：owla19s-ux/APS
- 本地：/Documents/APS
- 其他资源
```

资源通过对应 Connector 访问。APS 不默认复制或同步这些资源。

原先的 Project Address 概念调整为：**资源 / 地址是连接所指向的内容，不是空间本身。**

## 五、三页总览

```
APS
├─ 空间页
│  └─ 空间连接 / Context 的主要人机工作面
├─ 对话页
│  └─ 独立 AI 对话 / 查询 / 测试
└─ 设置页
   └─ 全局连接与系统设置
```

## 六、空间页

**空间页 = 用户进入、选择和管理空间连接，并进入具体 Context 的主要人机工作面。**

主要展示和操作：空间、空间内部组织、Context、Context 资源、任务、对话、状态、工作记录、验证、连接和调度相关状态。

空间名称、组织名称、Context 显示名称均由用户定义。

空间页可以展示和管理当前可用连接，例如 AI、GitHub、本地、设备、插件及其他服务。调度状态和结果也可以在此展示。

APS 不固定 Decision AI、Worker AI、AI A / AI B 或永久主 AI。具体由调度和连接状态决定。

AI 的口头结果不能直接作为事实状态，需要结合实际结果、验证或其他证据形成工作记录。

## 七、对话页

### 1. 定位

**对话页是 APS 的独立 AI 使用入口，不是第二个 Context 工作面，也不是一个新的 Dashboard。**

其核心用途是：

- 直接选择 / 切换一个 AI 连接；
- 进行普通 AI 对话；
- 查询、分析和测试；
- 在用户授权范围内调用其他连接；
- 查看实际调用结果及必要的验证结果。

对话页的交互母版沿用 Context 工作面中的“对话 + 输入”交互，不另造一套聊天产品式结构。

### 2. 基本结构

手机端保持简单的单页对话结构：

\`\`\`
┌──────────────────────────┐
│ 对话                  ⋯ │
├──────────────────────────┤
│ AI：GPT-5.6 Luna      ▾ │
├──────────────────────────┤
│                          │
│ AI：……                   │
│ 用户：……                 │
│ AI：……                   │
│                          │
│ [实际连接调用 / 结果]     │
│                          │
├──────────────────────────┤
│ ＋  输入消息……       ↑  │
└──────────────────────────┘
\`\`\`

其中：

- 顶部用于当前 AI 连接及相关操作；
- 中间是当前对话记录；
- 输入区保持原版 Context 工作面的简单输入方式；
- \`＋\` 用于选择需要提供给 AI 的其他连接或资料；
- 实际连接调用和结果应能与普通 AI 回复区分。

不增加固定的“工作区 / 工具区 / 任务区 / Dashboard”一级页面。

### 3. AI 选择

对话页可以选择或切换 AI 连接。

AI 不被固定定义为“主 AI”“施工 AI”“决策 AI”等角色。对话页中的 AI 只是当前直接使用的 AI 连接。

如果当前 AI 无法完成某项操作，可以由用户切换其他 AI；是否允许调用其他 AI 或其他连接，取决于当前授权和连接能力。

### 4. 连接调用

独立对话可以按需调用：

- 本地资源；
- 云端资源；
- GitHub；
- 文件；
- 空间；
- Context；
- 其他插件或服务连接。

调用不意味着对话页自动拥有这些连接的全部权限。

\`\`\`
用户输入
   ↓
AI 理解 / 决定是否需要连接
   ↓
用户授权范围内调用连接
   ↓
实际执行
   ↓
实际结果
   ↓
返回对话
\`\`\`

**AI 说“已经完成”不等于连接实际执行完成。**

如果发生文件修改、GitHub 修改、资源写入等实际操作，应以连接返回的实际结果及必要的验证结果作为事实依据。

### 5. 与 Context 的关系

对话页**不要求预先绑定 Context**。

没有绑定 Context 时：

- 可以直接与 AI 对话；
- 可以按授权使用可用连接；
- 不自动继承任何 Context 的资源和权限。

关联 Context 后：

- 当前对话可以读取该 Context 允许访问的资源；
- 调用连接必须遵守该 Context 的权限；
- 涉及实际修改时，必须遵守 Context 对连接及操作的授权；
- 对话记录可以作为该 Context 的工作记录之一。

因此：

\`\`\`
独立对话
   │
   ├── 不关联 Context → 独立使用连接
   │
   └── 关联 Context → 遵守 Context 权限
\`\`\`

关联 Context 不意味着自动启动 Context 的三阶段任务调度。

### 6. 与 Context 工作面对话的区别

两者使用相同的基础对话交互，但入口和语义不同：

| 项目 | Context 工作面对话 | 独立对话页 |
|---|---|---|
| 入口 | Context 内 | APS 对话页 |
| 核心用途 | 当前 Context 的工作记录与处理 | 直接使用 AI |
| Context | 已经处于当前 Context | 可不关联 |
| 待处理任务 | 直接关联当前 Context 任务 | 不强制存在 |
| AI | 作为当前 Context 可用连接 | 当前直接使用的 AI 连接 |
| 多连接调用 | 由 Context 调度 / 权限约束 | 按当前授权按需调用 |
| 输入 | 原版 Context 输入 | 沿用同一输入交互 |
| 实际结果 | 记录到 Context 工作过程 | 显示在当前对话，并可形成记录 |

独立对话页不是 Context 工作面的替代品；Context 工作面也不是独立对话页的必经入口。

### 7. 第一阶段边界

第一阶段对话页只保留：

- AI 选择 / 切换；
- 对话记录；
- 简单输入；
- \`＋\` 连接 / 资料选择；
- 实际连接调用结果；
- 必要的执行 / 验证状态。

暂不增加：

- 固定 AI 角色体系；
- 独立 Dashboard；
- 强制任务模式；
- 强制三阶段调度入口；
- 复杂工作流编辑器；
- 与 Context 无关的复杂项目管理功能。

## 八、设置页

**定位：全局连接与系统设置。**

设置页负责管理 APS 的全局连接、系统级权限和全局配置，不承载具体 Context 的工作过程。

### 1. 基本交互

设置页沿用 APS 当前 UI 的**点击展开 / 收起**交互，不采用独立 Dashboard 或复杂设置首页。

初始状态只显示一级设置区域：

```
┌──────────────────────────┐
│ 设置                  ⋯ │
├──────────────────────────┤
│                          │
│ 连接与服务            ›  │
│                          │
│ 权限                  ›  │
│                          │
│ 验证                  ›  │
│                          │
│ 系统                  ›  │
│                          │
└──────────────────────────┘
```

点击某个区域后，在当前页面直接展开：

```
连接与服务              ˅
────────────────────────

AI / API             ›
GitHub               ›
其他连接              ›
插件 / 服务           ›


权限                  ›
验证                  ›
系统                  ›
```

再次点击一级区域即可收起。

**原则：收起时保持简洁，展开后直接操作，不增加第二层“配置按钮”作为中间入口。**

一级区域内部也可以继续采用同样的点击展开 / 收起方式。例如点击“AI / API”后，可以直接展开已配置的 AI 连接及添加操作。

### 2. 全局连接

“连接与服务”负责管理 APS 的全局连接，包括：

- AI / API 连接；
- GitHub 连接；
- 其他全局连接；
- 插件及服务连接；
- 连接所需的认证、地址和基础配置。

展开后直接显示和管理对应连接，例如：

```
AI / API                ˅
────────────────────────

GPT-5.6 Luna             ●
Claude                   ●
其他 AI                  ○

＋ 添加 AI / API
```

AI / API、GitHub 等具体连接可以继续展开到连接详情，用于：

- 查看已连接项目；
- 增加、删除、启用或停用连接；
- 配置连接名称；
- 配置地址；
- 配置认证信息；
- 配置模型等基础参数；
- 进行连接测试。

连接在设置页完成全局配置，具体 Context 再决定是否使用以及授予什么权限。

### 3. 系统级权限

“权限”用于管理 APS 层面的通用权限，例如：

- 连接访问权限；
- 本地资源访问权限；
- 文件访问权限；
- 其他系统级能力授权。

Context 内 AI 的“拆分 / 做 / 审查”三个权限仍由 Context 自己管理，不在这里替代。

### 4. 验证能力

“验证”作为可展开的设置区域保留，但**第一阶段只保留验证能力的设置入口和概念，不实现复杂的统一自动验证机制。**

原因是不同连接的“完成证明”方式不同。GitHub、文件、本地资源、API、设备等连接，其实际结果和可验证证据并不统一，当前阶段不应为了统一界面而强行设计一套不可靠的自动验证系统。

展开后保持简单：

```
验证                  ˅
────────────────────────

验证能力
暂未启用复杂自动验证

说明：
不同连接的实际结果和验证方式不同，
后续根据具体连接逐步增加。

后续扩展
```

当前阶段不要求用户配置复杂的验证规则，也不要求 APS 对所有连接自动判断“是否真正完成”。

具体执行结果仍应区分：

```
AI / 连接返回
      ↓
实际执行结果
      ↓
验证（第一阶段暂不强制统一自动化）
```

因此：

- AI 的口头“完成”不能直接作为事实；
- 有明确实际结果时，优先展示实际结果；
- 暂时无法可靠验证时，不伪造“已验证”；
- 后续可以针对具体连接逐步增加可靠的验证方式。

验证机制属于后续扩展能力，当前不作为第一阶段核心功能实现。

### 5. 系统设置

“系统”作为可展开的设置区域，用于管理 APS 本身的通用系统设置，例如：

- 通知；
- 外观；
- 不同系统导航方式下的界面适配；
- 其他全局系统设置。

系统设置同样采用点击展开 / 收起，不单独设计复杂 Dashboard。

### 6. 设置页边界

设置页负责：

```
设置
├── 连接与服务
│   ├── AI / API
│   ├── GitHub
│   ├── 其他连接
│   └── 插件 / 服务
├── 权限
├── 验证
└── 系统
```

这些内容都是 APS 全局配置。

以下内容不放入设置页：

- 具体 Context 的工作任务；
- Context 内 AI 的拆分 / 做 / 审查权限；
- Context 的具体工作记录；
- Context 专属资源操作；
- 强制三阶段任务入口；
- 独立 Dashboard。

设置页与 Context 工作面的关系保持：

```
设置页
  └── 全局连接 / 全局权限 / 系统配置
          ↓
Context 工作面
  └── 使用哪些连接 + 授予哪些 Context 权限
```

## 九、页面边界

```
                    APS
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        空间页      对话页      设置页
          │          │           │
       空间连接      AI连接      全局连接
          │
       Context
          │
    连接 + 调度 + 内容
```

UI 页面只是 APS 的人机表现层，不重新定义 APS 的核心语义。

## 十、已废弃的 UI 模型

以下模型不再作为 APS 当前 UI 的正式概念：

- Project 作为 APS 顶层 UI 概念；
- Project Address 作为空间唯一地址；
- 一个 Project 对应一个主要资源地址；
- 空间 = 一个 Context；
- Context = 空间名称；
- AI 作为 Context 的固定组成部分；
- Decision AI / Worker AI / AI A / AI B 等固定角色分类；
- 工作区作为独立一级业务页面；
- 通过 AI 角色直接定义决策 / 施工职责；
- 复杂 Project Dashboard。

“项目”可以是用户自定义的 Context 名称，也可以用于描述一种组织方式，但不是 APS 的固定顶层 UI 概念。

## 十一、UI 与语义层的固定映射

当前正式 UI 以原版项目工作面的交互为母版，不把 Context 拆成固定的“内容 / 任务 / 对话 / 资源 / 连接 / 记录”一级页面。

```
空间
 ├── 分组
 └── Context 列表
      ↓ 点击
   Context 工作面
      ├── 顶部信息
      ├── 连接与配置（可展开 / 收起）
      │    ├── AI 成员
      │    ├── 地址 / 资源
      │    ├── 资料文件地址
      │    └── 项目配置
      ├── 待处理
      ├── 对话
      └── 输入
```

APS 的核心关系：

```
APS
├── 连接
│    ├── 空间
│    ├── AI
│    ├── GitHub
│    ├── 本地资源
│    └── 其他连接
└── 调度
```

## 十二、Context 工作面正式交互

### 1. 原版交互母版

```
Context 列表
   ↓
点击 Context
   ↓
Context 展开成为当前主要工作面
   ↓
连接与配置 / 待处理 / 对话 / 输入
   ↓
收起
   ↓
恢复 Context 列表
```

这不是 Dashboard，也不是多级 Context 管理页面。

### 2. 连接与配置

连接与配置是一个整体的可展开 / 收起区域。

**收起：**

```
连接与配置                    ›
AI成员：3
```

收起状态只显示 AI 成员数量，不直接管理成员和地址。

**展开：**

```
连接与配置                    ˅

AI成员
3 个
＋ 增加    替换    删除

权限
          拆分    做    审查
AI-1       ○      ●      ○
AI-2       ●      ○      ●
AI-3       ○      ●      ●

三个权限开关横向排列，由用户手动开启 / 关闭。每个 AI 的三个开关彼此独立；用户可按需要给同一 AI 开启一个、多个或全部权限。

地址
├── GitHub
│   └── owla19s-ux/APS
├── 本地目录
│   └── /Documents/APS
└── 其他地址

资料文件地址
└── 本地或云端

项目配置
├── 基本信息
├── 调度相关设置
└── 其他项目级设置
```

展开后直接管理，不增加第二层“配置按钮”。

### 3. AI 成员

AI 是 Context 可使用的连接成员。

- 一个 Context 可以有多个 AI 成员；
- 可以增加、删除、替换；
- AI 不永久绑定“主 AI / 施工 AI / 决策 AI”等身份；
- **三个第一阶段任务权限由用户通过开关分别授予 AI 成员。**

三个权限为：

- **拆分权限**：允许该 AI 承担任务拆分；
- **做权限**：允许该 AI 执行任务、调用连接并进行实际修改；
- **审查权限**：允许该 AI 检查实际执行结果并进行审查。

示例：

```
AI-1
├── 拆分  ON
├── 做    OFF
└── 审查  OFF

AI-2
├── 拆分  OFF
├── 做    ON
└── 审查  OFF

AI-3
├── 拆分  OFF
├── 做    OFF
└── 审查  ON
```

用户可以按需要开启或关闭任意 AI 的上述权限。权限是**能力授权**，不是永久角色名称；同一个 AI 可以同时拥有多个权限，也可以只拥有其中一个。

其中“做权限”属于实际修改权限。对于同一个正在执行的任务，同时只能由一个获得“做权限”的 AI 执行实际修改，避免多个 AI 同时施工造成冲突。

调度器根据用户开启的权限和当前任务状态，从具备相应权限的 AI 中选择执行者。

### 4. 地址

GitHub、本地目录、云端目录 / 文件等属于地址 / 资源来源。

本地目录不限于代码，可以包含文档、PDF、APK、图片、模型、数据、下载文件及其他资料。

GitHub 是一种云端地址来源，但云端不等于 GitHub。

APS 不因关联地址就自动复制或同步资源。

### 5. 资料文件地址

每个 Context 可以配置资料文件地址，支持本地或云端。

资料文件地址用于参考文档、APK、图片、设计资料、代码及其他工作资料。

**资料文件地址不是同步目录，也不等于 Context 的唯一地址。**

### 6. 待处理、对话与输入

保留原版项目工作面：

- **待处理**：当前待办任务；
- **对话**：Context 内历史工作记录；
- **输入**：当前 Context 展开后使用的输入区。

任务继续采用原版“勾选 → `@任务` 进入输入框”的交互。

任务是工作对象，不是 AI 工作模式。

### 7. 底部上下按钮与屏幕适配

原版 Context 工作面右下角的上下按钮属于**屏幕布局适配控制**，不是业务状态或工作区导航。

其用途是适配不同手机的系统导航方式和底部可用区域，尤其包括：

- 全面屏 / 手势导航；
- 带系统导航栏的传统导航方式。

按钮用于调整底部区域的适配状态，避免输入区、操作区等内容受到系统导航区域影响。

**这两个按钮不用于：**

- 切换 Context；
- 展开 / 收起 Context；
- 切换任务、对话或配置状态；
- 改变调度状态。

因此后续 UI 重构时应保留其原有的屏幕适配语义，不应将其重新解释为业务功能按钮。

### 8. 调度与实际结果

调度不增加永久 Dashboard。任务运行时只显示紧凑状态：

```
正在处理：任务名称
使用连接：AI / GitHub / 本地……
状态：运行中
```

第一阶段任务调度暂定为三个工作阶段：

```
用户任务
   ↓
【拆分】
   ↓
产生执行任务
   ↓
【做】
   ↓
实际执行结果
   ↓
【审查】
   ↓
通过 → 完成
   │
   └─ 不通过 → 返回【做】
```

三个阶段定义：

- **拆分**：理解任务、拆成可执行事项、确定执行顺序；执行者必须具有“拆分”权限；
- **做**：执行具体任务、调用连接、进行实际修改；执行者必须具有“做”权限；
- **审查**：检查实际执行结果是否正确、是否达到任务要求；执行者必须具有“审查”权限。

AI 不因为成员身份自动获得任何上述权限。用户通过每个 AI 成员的三个开关决定其可承担的阶段。

例如同一个 Context 有三个 AI 时，可以由 AI-1 拆分、AI-2 做、AI-3 审查；也可以由一个 AI 同时承担拆分和审查，或者根据用户设置由多个 AI 具备同一阶段的候选资格。

“做”权限是当前任务的实际修改权限。调度器从用户授权的“做”候选 AI 中选择一个执行者；同一任务同一时间只能有一个执行 AI 进行实际修改。

调度器负责组织三个阶段，但必须依据实际执行结果推进状态，不能把 AI 的口头“已完成”直接当作执行事实。

执行关系：

```
任务
 ↓
调度
 ↓
选择 / 调用连接
 ↓
执行
 ↓
实际结果
 ↓
审查 / 记录
```

必须区分：

```
AI / 连接返回
      ↓
实际执行结果
      ↓
审查结果
```

AI 的口头结果不能直接作为事实状态。

## 十三、当前 UI 边界

### 保留

- 原版项目 / Context 列表；
- 点击后展开为主要工作面；
- 原版待处理、对话、输入交互；
- 连接与配置折叠区域；
- AI 成员增删替换；
- **AI 成员的拆分 / 做 / 审查三个权限开关；**
- 地址 / 资源管理；
- 资料文件地址；
- **底部上下按钮的屏幕导航适配功能**；
- 紧凑的调度、执行和验证状态；
- **第一阶段“拆分 → 做 → 审查”的三阶段任务调度。**

### 明确不做

- 不把 Context 做成文件同步器；
- 不把“内容 / 资源 / 连接 / 任务 / 记录”做成固定一级导航；
- 不把 AI 做成固定 Context 角色；
- 不把 GitHub 视为唯一云端；
- 不把本地目录限定为代码；
- 不增加第二层配置按钮；
- 不用新的 Dashboard 式页面替换原版项目工作面；
- 不要求用户理解“Context / 上下文”这一内部术语；
- **不把底部上下按钮重新定义为业务导航或工作区控制。**
- **第一阶段不扩展超过“拆分 / 做 / 审查”的任务职责模型。**

## 十四、后续 UI 细化范围

后续只继续细化：

1. 空间页与 Context 列表的视觉布局；
2. Context 工作面的手机端布局；
3. “连接与配置”的展开 / 收起交互；
4. 任务、对话、输入区的视觉细节；
5. AI 成员三个任务权限开关的 UI；
6. 任务执行、实际结果和验证状态的展示；
7. **不同系统导航方式下的底部区域适配。**

后续不得重新引入已废弃的 Context Dashboard 或固定多页面导航结构。
