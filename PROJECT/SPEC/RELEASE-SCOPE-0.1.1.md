# APS 0.1.1 基础版交付范围

状态：当前版本施工基线

## 1. 版本定位

**0.1.1 是 APS 基础版，以完成当前已确认的产品设计落地为目标。**

本版本优先完成连接、项目上下文、对话、设置、本地文件、GitHub、软件开发结构及必要的施工 / 验证主链。以当前正式 UI、产品规格和架构文档为需求依据，不因发现未来版本的扩展需求而默认暂停当前施工。

本文件用于划定版本范围，不代表其中所有能力已经实现。实现状态必须由代码、测试和实际工作流证明。

## 2. 本版本必须落实的架构边界

### 2.1 模块与 APS 核心分离

- 外部库或独立服务通过 APS 内部适配边界接入。
- UI 和核心业务不直接依赖某个第三方模块的专有实现。
- 当前只需建立足以隔离实现的边界，不要求建立动态插件运行时或通用模块市场。
- 当前工程继续保持单 Android app 模块；是否拆分 Gradle 模块由实际收益决定。

### 2.2 配置与运行状态分离

- 连接 / 模块的身份、端点、模型、认证引用和权限配置属于配置数据。
- 当前连接状态、启动状态、最近错误、运行结果等属于运行状态。
- 两类数据不应依赖同一个临时 UI 状态来保存，也不得把凭证写入普通日志或展示文本。
- 0.1.1 只落实当前连接能力所需的最小分离，不建设完整生命周期管理系统。

### 2.3 统一能力接入边界

- AI/API、GitHub、Local/File 等能力通过明确的 Connection / Connector 适配边界提供。
- 公共层统一身份、能力声明、权限门禁、错误表达和必要的生命周期语义；具体业务方法保留类型化差异，不强迫所有连接实现无意义的同一套方法。
- 新增或替换某项实现时，尽量不改动无关业务和 UI。
- 权限由 APS 控制，第三方模块不得自行绕过授权直接执行写操作。

## 3. 0.1.1 交付范围

以当前正式需求文档为准，完成以下工作面和主链的实现及验证：

- Space → 目录 → Context 的组织与管理；
- Context 的名称、多个 Address、备注及所需资源关联；
- 普通对话、对话分组 / 管理、默认保存及可选关联 Context；
- 设置页中的 AI/API、GitHub、Local/File 连接配置与验证；
- AI 模型选择、连接状态、必要的错误提示与凭证边界；
- **最小运行诊断日志**：记录应用关键启动 / 运行阶段、崩溃或未捕获异常可用的诊断信息、API 连接测试与请求失败类别、耗时及结果；日志与用户项目资料分离，凭证、API Key、Authorization 头和敏感请求内容不得进入日志；
- Local 文件访问的授权、读取 / 修改能力及保存边界；
- GitHub 仓库访问、受控写入和实际 Workflow / Verify 结果查询；
- 软件开发结构的 UI → 功能 → 架构 → 施工项 / 卡 → 代码 / 产物 → 验证关系；
- 现有任务施工、结果核验和必要的状态持久化；
- 与上述范围直接相关的构建、单元测试、契约测试和主链验证。

具体功能是否已纳入需求，以当前正式 UI 与产品规格为准；本清单不授权扩张到完整 Agent Runtime 或未来模块平台。

## 4. 本版本明确不做

- 通用模块管理页面；
- 第三方模块的动态发现、下载、安装、升级、停用和卸载系统；
- 插件市场、任意代码动态加载或通用沙箱；
- 自动依赖解析、跨模块版本协调和通用回滚平台；
- 完整多 AI 并行施工协议、无限 Agent Loop 或完整 Workflow Engine；
- 与 0.1.1 已确认需求无直接关系的架构重写；
- 完整日志分析平台、远程崩溃上报 / 云端监控、复杂日志检索仪表盘、自动诊断根因或自动修复系统。

如发现此类需求，记录到 0.1.2 后续清单；只有发现会导致当前实现无法安全运行、无法构建或违反已确认需求的阻塞问题时，才升级为 0.1.1 阻塞项。

## 5. 施工与审查规则

1. **先判断影响范围**：问题影响当前版本、未来版本，还是仅属于改进建议。
2. **当前版本问题优先处理**：对已确认需求的功能缺失、数据丢失、权限绕过、构建失败和主链验证失败，应处理后再推进相关路径。
3. **未来问题登记，不自动停工**：不影响 0.1.1 的问题写入 0.1.2 文档，继续当前施工。
4. **限制审查范围**：一次变更围绕一个可验证目标；不借机审查或重构无关模块。
5. **证据决定完成状态**：提交成功不等于功能完成；按变更范围检查实际测试与工作流。
6. **不直接修改 main**：通过工作分支提交和验证，符合仓库规则后再合并。
7. **文档不冒充实现**：本文件定义目标和边界，不代表对应代码已实现。

## 6. 0.1.1 完成判定

- 当前正式 UI / 产品需求已逐项映射到实现或明确的未完成项；
- 三个模块边界落实到代码 / 接口和必要文档，不停留在口号；
- 核心连接与数据持久化路径有对应测试；
- 启动 / 运行异常、API 连接成功或失败均有可检查的诊断线索；日志记录本身失败时不得导致应用主流程崩溃；
- 相关 Android 构建、测试和 GitHub 工作流结果已实际确认；
- 未完成或受环境限制的项目如实列出，不用静态审查代替运行证据；
- 0.1.2 的未来需求已单独登记，不混入 0.1.1 的强制交付范围。
