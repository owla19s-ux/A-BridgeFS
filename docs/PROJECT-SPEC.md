# A-BridgeFS 项目需求功能书

更新时间：2026-09-30

> 统一记录需求、功能、UI、协作机制与值得保留的想法。
> 记录 ≠ 确认。状态随讨论、施工和真实验证推进。

## 一、当前项目方向

A-BridgeFS 当前定位为 AI 协作移动端控制入口。

当前第一实验：

人
→ A-BridgeFS
→ Decision AI / Worker
→ GitHub 项目
→ Commit / Verify
→ 回执
→ 人

当前优先真实运行，不急于平台化。

---

## 二、需求与功能

### R-001 Decision AI → Worker 连续施工

**状态：开发中 / 待验证**

一次明确的施工授权，应允许 Worker 在规定边界内连续完成当前阶段，而不是每个小动作都要求用户输入“继续”。

验收方向：
- 明确当前施工目标与边界。
- Worker 能连续处理普通实现问题。
- 正常 Commit / Verify / 重试不要求用户逐次输入“继续”。
- 真正需要决策时才暂停。
- 阶段完成后再汇报。

### R-002 小问题自主处理

**状态：开发中 / 待验证**

Worker 可自行处理明确、低风险、属于当前任务范围的小问题。

不得自行改变：
- 已确认的架构原则
- 用户明确的产品行为
- 任务范围
- 权限边界

### R-003 Decision AI 与 Worker 自动对接

**状态：已设计未实现**

Worker 遇到真正的决策级问题时，交给 Decision AI；获得决策后自动恢复施工。

Worker
→ 决策请求
→ Decision AI
→ 决策结果
→ Worker
→ 继续施工

第一版不做多 Decision AI、多 Worker 调度。

### R-004 Verify 工序确认

**状态：开发中**

Commit 后必须确认对应 Verify 是否真正触发，并读取真实结果。

事实链：

Commit SHA
→ Check Runs / Workflow Runs
→ Workflow Job
→ 实际结果

### R-005 A-BridgeFS 协作回执

**状态：开发中**

用户看到项目当前状态：
- WAITING
- RUNNING
- SUCCESS
- FAILURE
- BLOCKED

只显示必要信息，不展示 CI 内部流水账。

### R-006 协作日志

**状态：已设计未实现**

记录：
- 时间
- 项目
- 操作者
- 指令
- Worker 回执
- 状态
- Commit / Verify 关联

与运行日志、崩溃日志分离。

### R-007 权限边界

**状态：候选**

逐步验证：
- 读取仓库
- 修改代码
- Commit
- 测试
- PR
- 合并
- Secrets / 部署 / 仓库设置

原则：最小必要权限。

### R-008 等待外部工序

**状态：候选**

验证 Worker 是否能够理解等待原因、等待对象、负责工序、对应 Commit、继续条件以及恢复位置。

### R-009 多 API 管理

**状态：待讨论**

当前实际状态：API 设置页目前只能配置一个 API。

后续需要讨论是否支持多个 API，以及 API、Model、用途/角色之间的管理方式。

当前不施工。

## 四、当前 UI / 产品原则

- 移动端优先。
- 简洁、明确、低负担。
- 人看状态，AI 查日志。
- UI 解决人的理解和操作问题，不把内部复杂性全部暴露给用户。
- 实际手机截图作为 UI 判断依据之一。
- UI 想法先记录，确认后再进入正式施工。

## 六、状态定义

- **待讨论**：已经记录，但尚未形成明确决定
- **候选**：有价值，等待是否进入施工
- **已确认**：方向已经确定
- **开发中**：正在施工
- **已实现**：代码已完成，尚未完成最终验证
- **已验证**：真实测试确认
- **阻塞**：存在明确阻塞因素
- **废弃**：不再采用
