# A-BridgeFS V0.1 最小架构

状态：施工基线
日期：2026-09-28

## 1. 定位

A-BridgeFS V0.1 只验证一个核心闭环：

API + 对话 + 用户授权 + BridgeFS 本地执行 + 执行结果返回。

第一版不是完整 Agent 平台，也不是 MiniMax。

MiniMax、Weijia、NeuroMesh 等方向只保留未来接口，不在本版本实现。

## 2. 核心闭环

用户
↓
API / 本地对话
↓
AI
↓
本地操作请求
↓
用户授权规则
↓
BridgeFS
↓
Android 本地资源
↓
执行结果
↓
AI
↓
继续对话

API 与本地对话必须进入同一套执行流程，不建立两套本地执行系统。

## 3. API

第一版支持用户配置 API：

- API 地址
- API Key
- 模型

第一版先以通用 API 为主。

未来可以增加其他连接方式，但不影响本版本结构。

## 4. 对话

App 内提供最基本的聊天入口。

AI 可以：

- 正常回答用户问题
- 判断是否需要本地操作
- 提出本地操作请求
- 接收 BridgeFS 执行结果
- 根据结果继续对话

第一版不实现复杂多角色协作。

## 5. 用户授权

用户授权决定 AI 可以使用哪些本地能力。

授权至少包含：

- 目录范围
- 操作类型
- 风险等级

第一版支持三种结果：

- 允许
- 需要确认
- 禁止

已经授权且符合规则的普通操作，可以连续自动执行，不要求用户每次确认。

示例：

目录：/A3/A0项目/

允许：
- 查看
- 读取
- 写入
- 修改

禁止：
- 删除

## 6. BridgeFS

BridgeFS 是唯一的本地执行入口。

AI 不直接访问 Android 文件系统。

执行链：

AI
↓
操作请求
↓
BridgeFS 权限检查
↓
CommandParser
↓
PathSecurity
↓
CommandExecutor
↓
Android
↓
Receipt

第一版优先复用旧 BridgeFS 已验证资产：

- CommandParser
- CommandExecutor
- PathSecurity
- Foreground Service
- 本地文件读写
- 执行结果

第一版优先支持：

- list
- read
- write
- edit

## 7. 执行结果

BridgeFS 必须返回真实执行结果。

成功：

{
  "status": "SUCCEEDED",
  "command": "write",
  "resource": "测试.txt"
}

失败：

{
  "status": "FAILED",
  "command": "write",
  "resource": "测试.txt",
  "message": "..."
}

被权限拦截：

{
  "status": "DENIED",
  "reason": "permission"
}

AI 的自然语言不能替代真实执行结果。

## 8. 需要保留的接口

第一版只实现最小功能，但数据结构不要堵死未来：

- API 连接方式
- AI 角色
- 任务
- 权限
- 执行记录
- 输入入口

暂不实现：

- 多 AI 自动协作
- 书记员
- 自动调度
- 复杂记忆
- 项目管理
- 云同步
- 多设备
- NeuroMesh
- MiniMax 完整工作空间

## 9. 第一版验收

1. 添加 API。
2. 打开本地对话。
3. AI 能正常回答。
4. 用户授权一个目录。
5. AI 提出本地操作。
6. BridgeFS 检查授权。
7. BridgeFS 执行 list/read/write/edit。
8. 返回真实结果。
9. AI 能继续对话。
10. 授权范围内连续操作无需重复确认。
11. 超出授权范围被拦截。
12. 高风险操作进入确认或被禁止。

## 10. 设计原则

最小闭环优先。

已有 BridgeFS 能力优先复用。

AI 负责理解与提出操作，本地 BridgeFS 负责真正执行。

用户授权与每次确认不是一回事。

执行结果必须来自真实本地执行。

未来能力只留接口，不提前堆进第一版。
